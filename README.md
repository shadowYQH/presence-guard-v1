# 人影守望 · Presence Guard

一个 Android 摄像头应用：画面中出现人时持续播放提示音。**不依赖人脸**——背对镜头、侧身、戴口罩、蹲在桌下、只露出半个身子也能识别。全部推理在设备本地完成，不联网、不录像、不上传。

> 详细设计、参数表、实测数据、调参指南见 **[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)**
> 性能与加速器选型见 **[docs/PERFORMANCE.md](docs/PERFORMANCE.md)**

---

## 为什么不用人脸识别

人脸检测在真实监控场景里失效得太容易：人背对镜头、低头看手机、戴帽子口罩、距离稍远、光线偏暗，人脸模型就什么都给不出来。而这个应用的诉求是「画面里有没有人」，主体是人，不是脸。

所以检测的是**人体**：骨架 + 整体轮廓。

## 技术路线

两条互补的引擎并行跑，再融合。

| 引擎 | 模型 | 强项 | 弱项 |
|---|---|---|---|
| **姿态检测**（主） | ML Kit Pose Detection `accurate`，BlazePose 33 关键点 | 背对/侧身/蹲坐/半遮挡仍能出骨架；几乎不依赖人脸 | 远距离小目标关键点会糊掉 |
| **目标检测**（辅） | TFLite EfficientDet-Lite0（COCO person 类） | 整体外观检测，远处小目标更敏感 | 会把衣架、人形立牌、海报人物误判成人 |

姿态引擎用 **bundled** 版本，模型直接打进 APK，不依赖 Google Play 服务——国产机型、无 GMS 设备照常离线运行。

## 判定链路：五层过滤

精度不是靠单个模型堆出来的，而是靠「让不同类型的错误在不同层被拦掉」。

```
每帧图像
   │
   ├── 姿态引擎 ──► 关键点加权打分 + 几何合理性 ─┐
   │                                            ├── 空间融合（IoU / 包含关系）
   └── 目标检测 ──► person 置信度 ──────────────┘        │
        │（常规模式：整帧 + 瓦片滚动扫描）                ├── 面积门限（双向）
        │（选区模式：选区内裁切放大后两引擎都跑）         ├── 小目标轨迹持久化
        │                                                ├── 滑动窗口投票 N-of-M
        │                                                └── 迟滞状态机 → 提示音
```

1. **单帧证据分**：按部位加权，躯干（双肩双髋）最高、手腕脚踝最低；再乘以**与朝向无关**的几何校验系数（躯干长/肩宽、髋宽/肩宽、头到肩中点距离）。早期用过「双肩要水平」「髋必须在肩下方」，结果把躺着、侧身、横屏拍摄的人全判成误检——旋转不变量才是稳的。
2. **双引擎交叉印证**：两边都报 → 概率合成 `1-(1-a)(1-b)`；只有一边报 → 必须越过更高的单引擎门槛。
3. **面积门限（双向）**：太小丢弃（远处噪点）；单引擎给出几乎覆盖全画面的巨型框也丢弃（纯色墙面/壁纸），但双引擎一致时豁免。
4. **小目标轨迹持久化**：面积占比过小的候选不要求单帧高分（离得越远原始分天然越低），改为「低门槛 + 同一位置连续命中 N 帧」。真人会连续出现在同一位置，墙面图案、衣架这类误检往往偶发且位置飘忽。
5. **时序投票 + 迟滞**：最近 8 帧至少 4 帧命中且平滑分达标才进入；连续 14 帧无目标才退出。进入门槛高于退出门槛，人站在阈值边缘时不会反复报警。

## 五个关键设计

### 1. 双路合成：便宜的每帧跑，贵的滚动跑

一条路线不可能同时做到「便宜」和「看得清远处」，所以拆成两条：

- **快速路**：每帧整帧推理一次，负责近处大目标，成本固定且很低；
- **精细路**：画面切成 6×4 = 24 片（重叠 25%），每帧只滚 1~3 片，若干帧覆盖全图。

画面里已经有人时自动跳过精细路——报警已触发，瓦片的意义是「找人」，稳态下省掉这几次推理。空场景才是需要全力搜索的时候。

> 为什么不能靠提高采集分辨率：模型输入恒为 320×320，缩放会把分辨率增益完全抵消。**唯一有效的手段是缩小送进模型的视野。**

### 2. 多边形选区 + 选区内放大识别

在预览画面上点几个点圈出区域（数量不限），之后**只在这些多边形里判定**：

- 每个选区的外接矩形被裁出来送进模型，选区占画面 1/8 时相当于放大了 8 倍——是真·长焦，不是数码插值；
- 姿态和目标检测**都在放大后的裁切图上跑**，两个引擎的交叉印证才能继续压住「放大后噪点变成人」；
- 多个小选区靠**游标轮转**覆盖（每帧扫 1~2 个），配合小目标轨迹在跨帧累积证据；
- 选区本身就极强的空间先验，所以面积门限从 0.30% 放开到 0.02%，也不再要求攒帧确认。

实测：**选区模式 8fps，常规模式 3.5fps**——精度更高、速度还快一倍，因为预算花在了用户真正关心的区域上。

「省」这个字要说准确：选区模式**完全不生成整帧位图**，每块选区单独从 YUV 里挖矩形，
矩形外的像素一个都不解码（转换耗时 30ms → 3ms）。推理次数不变——模型输入恒为 320×320，
一次就是一次。选区的真正价值是把同样的推理预算**集中**到关心的区域。

### 3. 双指缩放 ≠ 换焦段

两条完全独立的「拉近」路径，界面上也分开显示：

| | 焦段按钮 | 双指缩放 |
|---|---|---|
| 实现 | 相机 `setZoomRatio()`（传感器级裁切） | 从帧里挖中间一块送模型 |
| 预览 | 跟着放大 | 不动，只画一个虚线框标出「框外不识别」 |
| 画质 | 真实像素，部分机型还会切长焦 | 像素不增加，放大到极限就是放大模糊 |

物理焦段受机型限制（本机只报了一颗后置），数字裁切永远可用；两者互补，不是替代关系。

### 4. 2 秒全图巡检：补「望远镜」的盲区

选区和数字裁切都看得清但看得窄。每 2 秒有一条旁路退回**当前镜头最广视野**扫一遍整帧，
只判「有没有人」，结论进独立的融合引擎，**不参与主判定、不投票**。命中就响。

前后双摄并发（CameraX 1.4 的 `ConcurrentCamera`）会尝试同时绑定另一面摄像头；
机型 HAL 不支持时自动降级为单镜头巡检，界面显示「巡检 单」。

### 5. 变焦 + 息屏持续运行

- **变焦**：1x/2x/3x/5x/8x 循环切换，走 CameraX 的 `setZoomRatio`——传感器级区域裁切，部分机型还会自动切长焦镜头，分析流拿到的是真实的放大像素。后置多摄机型还会额外出现「镜头」按钮切换物理镜头。
- **息屏**：相机管线跑在前台服务里（`foregroundServiceType="camera"` + `PARTIAL_WAKE_LOCK`），绑定服务自己的 `LifecycleOwner`，切后台、熄屏都继续检测。
- **预览功耗治理**：`Preview.setSurfaceProvider(null)` 并不能停掉预览的那条相机输出流，必须把 Preview 用例从绑定列表里去掉。实测预览约占 15% 单核，熄屏后这部分**完整归零**（CPU 13~17% → 0.0%），检测不受影响。触发点用 `onPause` + `ACTION_SCREEN_OFF` 双保险——MIUI 熄屏时 `onStop` 不一定来。

## 灵敏度三档

同一套算法，只是阈值组合不同，行为可预期：

| 档位 | 进入阈值 | 投票 | 最小面积 | 小目标确认 | 适用 |
|---|---|---|---|---|---|
| 灵敏 | 0.44 | 3/8 | 0.12% | 连续 2 帧 | 远处的小个子、半身也要报 |
| 均衡 | 0.52 | 4/8 | 0.30% | 连续 3 帧 | 室内正常距离（默认） |
| 稳重 | 0.66 | 5/8 | 1.00% | 连续 5 帧 | 只要明确的大目标，几乎不误报 |

## 实测性能（Xiaomi M2007J1SC / 骁龙 865 / Android 13）

| 模式 | 转换 | 姿态 | 检测 | 帧间隔 | 帧率 |
|---|---|---|---|---|---|
| 常规 · 空场景（2 瓦片 + 整帧） | 40–50ms | 60–75ms | 210–230ms | ~280ms | ≈3.5 fps |
| 常规 · 已有人在（仅整帧） | ~45ms | ~70ms | ~80ms | ~200ms | ≈5 fps |
| **选区 · 1 个选区（放大识别）** | 37–45ms | 40–75ms | 85–160ms | 128–133ms | **≈7.5–8 fps** |

单次 EfficientDet-Lite0 推理实测 **~80ms**，是全局瓶颈。加速器选型做完整对比：

| 配置 | 单次推理 | 结论 |
|---|---|---|
| CPU（4 线程） | 82 ms | 基准 |
| GPU（TfLiteGpuDelegateV2，266/266 节点全部下沉） | 84 ms | **无收益**。深度可分离卷积太碎，GPU 调度开销吃掉并行收益 |
| NNAPI | 69 ms | 收益很小 |
| int8 量化模型 | 无法加载 | Task 库 JNI 报 `UnsatisfiedLinkError`，试过 MediaPipe 与 TF Hub 两个来源 |

输入尺寸扫描（160px→75ms，320px→74ms）证明瓶颈是模型自身计算量而非预处理。

CPU 占用（单核百分比）：检测 + 预览 106–130%；仅预览 13–17%；熄屏 0%。

## 提示音

不用系统 `ToneGenerator` 作主力——它走通知/系统音通道，手机静音或媒体音量为 0 就完全没声。

这里程序合成 PCM，走 **ALARM 通道**（唯一不会被媒体音量静音、且不需要前台焦点就能出声的通道），静音时界面会提示闹钟音量为 0。人持续在场时按设定间隔（默认 1.5s）反复提醒，人离开立即清零，下次出现立刻响。

## 构建

需要 JDK 17+ 与 Android SDK（compileSdk 34）。可直接用 Android Studio 打开，或命令行：

```bash
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

APK 约 **56MB**，体积几乎全部来自 ML Kit 姿态模型的 native 库与内置模型文件（`pose_landmark_detector_full_f16` 6.4MB + `efficientdet_lite0` 4.5MB）。这是「不依赖 Google Play 服务、可离线」的代价。已剔除 ML Kit 合并进来的无关权限（INTERNET、READ_PHONE_STATE、外部存储、开机自启等），安装时只需要相机与振动权限。

`abiFilters` 只保留 `arm64-v8a`（去掉 32 位省约 35MB）。

## 已知限制

- **广场级密集小目标**（25–45px 的人体）到不了可靠阈值。这是 EfficientDet-Lite0 在 320×320 输入下的能力边界，同模型在湖景远景（40–80px）能到 0.75。要突破必须换 640 输入的模型（见 [v2 仓库](https://github.com/shadowYQH/presence-guard-v2-yolo)）。
- **解锁回前台时预览有几百毫秒黑屏**：这是「彻底关掉预览流」的代价。
- **物理镜头切换**只在多摄机型上出现；本机实测只暴露 1 颗后置相机，所以只有变焦可用。
- **前后双摄并发依赖相机 HAL**。本机明确返回 `Concurrent camera is not supported on the device`，自动降级为单镜头巡检（按钮显示「巡检 单」）。
- **双指缩放不增加像素**。数字裁切到 6x 时送进模型的是一小块放大图，和真的长焦不是一回事。
- **选区是图像空间坐标**：改变变焦后画面内容会变，选区仍停在屏幕同一位置（语义上视为「盯住这个方向」）。
- **长时间运行会发热**，建议接电源。
