# 人影守望 · Presence Guard

一个 Android 摄像头应用：画面中出现人时播放提示音。**不依赖人脸**——背对镜头、侧身、戴口罩、蹲在桌下、只露出半个身子也能识别。

---

## 为什么不用人脸识别

人脸检测/人脸识别在真实监控场景里失效得太容易：人背对镜头、低头看手机、戴帽子口罩、距离稍远、光线偏暗，人脸模型就什么都给不出来。而这个应用的诉求是「画面里有没有人」，主体是人，不是脸。

所以本方案检测的是**人体**：骨架 + 整体轮廓。

## 技术路线

两条互补的引擎并行跑，再融合。

| 引擎 | 模型 | 强项 | 弱项 |
|---|---|---|---|
| **姿态检测**（主） | ML Kit Pose Detection `accurate`，BlazePose 33 关键点 | 背对/侧身/蹲坐/半遮挡仍能出骨架；几乎不依赖人脸 | 远距离小目标关键点会糊掉；只露一截身体时骨架不完整 |
| **目标检测**（辅） | TFLite EfficientDet-Lite0（COCO person 类） | 整体外观检测，远处小目标更敏感，能框出完整外轮廓 | 会把衣架、人形立牌、海报人物误判成人 |

姿态引擎用 **bundled** 版本，模型直接打进 APK，不依赖 Google Play 服务——国产机型、无 GMS 设备照常离线运行。

## 判定链路：五层过滤

精度不是靠单个模型堆出来的，而是靠「让不同类型的错误在不同层被拦掉」。

```
每帧图像
   │
   ├── 姿态引擎 ──► 关键点加权打分 ─┐
   │                                ├── 空间融合（IoU / 包含关系）
   └── 目标检测 ──► person 置信度 ──┘        │
        │（整帧没检出时）                    ├── 面积门限（滤掉远处噪点）
        └──► 瓦片深扫（切片推理） ──────────┤
                                            ├── 小目标轨迹持久化
                                            │
                                            ├── 滑动窗口投票 N-of-M
                                            │
                                            └── 迟滞状态机 ──► 有人 / 无人
                                                              │
                                                              └──► 提示音
```

### 第 1 层：单帧证据分

姿态引擎不只看「有没有关键点」，而是按部位加权：躯干（双肩 + 双髋）权重最高，头部次之，手腕脚踝最低。只匹配到一只手腕时得分会被压到 0.4 以下——那更可能是误匹配，不是人。

```
score = 0.70 × min(1, 加权证据 / 5.0) + 0.30 × 关键点平均置信度
若躯干关键点一个都没命中 → 再 × 0.55
再乘以几何合理性系数（与朝向无关的人体比例校验）
```

几何校验只用**旋转不变量**：躯干长度 / 肩宽、髋宽 / 肩宽、头到肩中点的距离。早期版本用过「双肩要水平」「髋必须在肩下方」，结果把躺着、侧身、以及手机被横过来拍的人全判成了误检——人躺沙发上或镜头本身就是斜的，这两条约束会无条件失效。

### 第 2 层：双引擎交叉印证

两个引擎的框做 IoU 与包含关系匹配：

- **两边都报**（同一位置）→ 分数按「至少一个为真」的概率合成 `1-(1-a)(1-b)`，直接采信。
- **只有姿态报** → 必须越过更高的 `poseOnlyMinScore` 才采信。
- **只有检测报** → 必须越过 `detectorOnlyMinScore`，且分数按目标大小折扣（远处小框即使置信度高也可能是杂物）。

这一层是压误报的主力：衣架被 EfficientDet 认成人时，因为姿态引擎出不了骨架，分数过不了门槛，直接丢弃。

### 第 3 层：面积门限

目标框占画面比例低于 `minAreaRatio` 的直接丢弃，避免把远处的挂钟、花瓶、墙角阴影放大成「人」。

反过来，几乎覆盖整幅画面的框如果是**单引擎**给出的，也丢弃——那通常是纯色墙面、桌面壁纸被当成了人；但双引擎都同意时保留，那是贴着镜头拍的真实人体。

### 第 4 层：双路合成 + 小目标轨迹持久化

这是「远处的人」能不能识别出来的关键。

EfficientDet-Lite0 的输入固定 320×320，整帧缩放后十几米外的人只剩二三十像素，特征基本消失。**提高采集分辨率没有用**——缩放会把增益抵消掉，唯一有效的手段是缩小送进模型的视野。所以做了三件事：

0. **双路合成**：一条路线不可能同时做到便宜和看得清远处，所以拆成两条——
   - *快速路*：每帧对整帧跑一次推理，负责近处大目标，成本固定；
   - *精细路*：把画面切成 6×4 = 24 片，每帧只滚 2~3 片（随灵敏度），若干帧覆盖全图。
   画面里已经有人时自动跳过精细路（报警已触发，瓦片的意义是「找人」），帧率直接翻倍。


1. **瓦片深扫（切片推理，SAHI 思路）**：整帧没检出人时，把画面裁成 2×2 带重叠的瓦片分别推理，人在这片里占的比例被放大约 1.7 倍，等于凭空提了分辨率。每帧只扫 2 片、游标轮转，覆盖全部瓦片约需 2 帧。
2. **用时间证据替代空间置信度**：面积占比低于 `smallTargetAreaRatio` 的候选不再要求单帧高分（离得越远原始分天然越低，任何「先打折再比门槛」的做法都会把人越推越远），改为「低门槛 + 同一位置连续命中 N 帧」。真人会连续出现在同一位置，而墙面图案、衣架这类误检往往偶发且位置飘忽。

### 第 5 层：时序投票 + 迟滞

单帧命中不算数：

- 进入：最近 8 帧里至少 4 帧命中，**且** EMA 平滑分 ≥ 进入阈值
- 退出：连续 14 帧无目标，**且** 平滑分 < 退出阈值

进入阈值高于退出阈值（迟滞 / hysteresis），人站在阈值边缘时不会反复报警。报警本身还有 3.5 秒冷却。

## 灵敏度三档

同一套算法，只是阈值组合不同，行为可预期：

| 档位 | 进入阈值 | 投票 | 最小面积 | 小目标确认 | 适用 |
|---|---|---|---|---|---|
| 灵敏 | 0.44 | 3/8 | 0.12% | 连续 2 帧 | 远处的小个子、半身也要报 |
| 均衡 | 0.52 | 4/8 | 0.30% | 连续 3 帧 | 室内正常距离（默认） |
| 稳重 | 0.66 | 5/8 | 1.00% | 连续 5 帧 | 只要明确的大目标，几乎不误报 |

> 测试远处目标时用「灵敏」档：它把最小面积门限放宽到 0.12%（480×640 下约 370 像素，
> 相当于 20 米外人体的占屏比例），小目标只需连续 2 帧即可确认。

## 实测性能（Xiaomi M2007J1SC / 骁龙 865 / Android 13）

单次 EfficientDet-Lite0 推理实测 **~80ms**，这是全局瓶颈。做过完整选型对比：

| 配置 | 单次推理 | 结论 |
|---|---|---|
| CPU（XNNPACK，4 线程） | 82 ms | 基准 |
| GPU（TfLiteGpuDelegateV2，266/266 节点全部下沉） | 84 ms | **无收益**。fp32 卷积在 Adreno 的 OpenCL 上并不快 |
| NNAPI | 69 ms | 收益很小，且首次预热数秒 |
| int8 量化模型 | 无法加载 | Task 库 JNI 报 `UnsatisfiedLinkError`，试过 MediaPipe 与 TF Hub 两个来源 |

输入尺寸扫描证明瓶颈确实是模型本身而非预处理：160px 输入 75ms、320px 输入 74ms，
耗时与输入大小无关（模型输入恒为 320×320）。

实时链路的实测分段耗时（1080p 采集）：

| 场景 | 转换 | 姿态 | 检测 | 帧耗时 | 帧率 |
|---|---|---|---|---|---|
| 画面有人（跳过瓦片） | 29ms | 60ms | 60ms | ~100ms | **~10 fps** |
| 空场景（2 片瓦片） | 29ms | 60ms | 195ms | ~220ms | **~4.5 fps** |

姿态与检测并行跑在独立线程，帧耗时取两者较大值，不是相加。

## 提示音

没有用系统 `ToneGenerator` 作主力——它走通知/系统音通道，手机静音或媒体音量为 0 时就完全没声。

这里程序合成 PCM（880Hz 短音 + 1320Hz 长音，带指数衰减包络），走 **ALARM 通道**，静音模式下依然能响；同时附带一次短振动。界面启动时会检测闹钟音量，为 0 会提示。

## 构建

需要 JDK 17+ 与 Android SDK（compileSdk 34）。推荐直接用 Android Studio 打开 `PresenceGuard/` 目录。

命令行：

```bash
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

APK 约 **69MB**，体积几乎全部来自 ML Kit 姿态模型的 native 库（`libxeno_native.so` 21MB × 2 个 ABI）与内置模型文件（`pose_landmark_detector_full_f16` 6.4MB + `efficientdet_lite0` 4.5MB）。这是「不依赖 Google Play 服务、可离线」的代价；如果设备确定有 GMS，改用 `com.google.android.gms:play-services-mlkit-pose-detection` 可以把体积压到 20MB 以内。

已剔除 ML Kit 合并进来的无关权限（INTERNET、READ_PHONE_STATE、外部存储、开机自启等），安装时只需要相机与振动权限。

## 已知限制

- **只在前台工作**：Activity 退出或锁屏后分析停止。屏幕常亮已开启，适合当「值守」用；真要做后台监控需要加前台服务（`foregroundServiceType="camera"`），当前未实现。
- **功耗**：两个模型并行推理，中端机约 10~15fps，持续运行会发热。长时间值守建议接电源。
- **隐私**：全部推理在设备本地完成，不联网、不存图、不上传。
